# E-Doc (Electronic Document) Module — Data Schema Design

**Database**: `edoc_tasaeng` (MySQL, on apis.com.la)
**Scope of this doc**: Data tables required for the new "e-Doc (electronic document)" module (Module 1).
**Approach**: These tables are **added to the same `edoc_tasaeng` database**, coexisting with the
existing budget/finance module, and use the dedicated prefix **`edoc_`** so they are easy to
identify and maintain separately.

---

## 1. Modules & Naming Convention

The system is split into two modules (agreed with the boss):

| Module | Focus | Table prefix |
|---|---|---|
| Budget / Finance (existing) | Chart of accounts, budget plans, journal, payments, organizations, user permissions | `acc_` `gen_` `payment_` `ap_` | 
| **e-Doc (new)** | Document catalog, citizen applications, approval/signing, QR fee payment, download, statistics, administrative roll-up | **`edoc_`** |

The `edoc_` tables connect to existing tables via `off_id` (administrative unit) and `ac_code`
(revenue account).

---

## 2. New Tables Overview (all prefixed `edoc_`)

### 2.1 Master / Reference Data

| Table | Description | Key fields |
|---|---|---|
| `edoc_doc_type` | Document categories (14: certification, application, proposal, loss report, memorandum, contract, sale documents, ownership transfer, fine, permit, change of use, mediation, registration) | `id`, `doc_type_code`(01..14), `name_lo`, `name_en` |
| `edoc_doc_item` | Document item catalog = the 51 documents from the requirements, with price, unit, category | `id`, `doc_type_id`, `name`, `unit`, `price`, `is_active` |
| `edoc_service_fee` | Service/handling fees (price schedule per item, may override catalog price) | `id`, `doc_item_id`, `fee_type_id`, `amount` |
| `edoc_fee_type` | Fee types (fee, tax, land tax, service fee…) | `id`, `fee_type`, `name_lo` |

### 2.2 Administrative Hierarchy (Village → Tasseng → District → Province) Roll-up

The requirement aggregates from village level upward: Village → Tasseng (commune) → District →
Province. Four level tables carry this hierarchy.

| Table | Description |
|---|---|
| `edoc_province` | Province |
| `edoc_district` | District/Municipality (parent = `province_id`) |
| `edoc_tasseng` | Tasseng/commune level (parent = `district_id`) |
| `edoc_village` | Village (parent = `tasseng_id`; links `off_id` → `ap_office` for consistency with the budget side) |

Roll-up is done bottom-up by `province → district → tasseng → village` JOINs, giving
"village aggregated to tasseng, tasseng to district, district to province".

### 2.3 Citizens / Applicants

| Table | Description | Key fields |
|---|---|---|
| `edoc_citizen` | Citizen / applicant (mobile app user), registered by phone or email | `id`, `phone`, `email`, `password_hash`, `full_name`, `id_card`, `village_id`, `dob`, `gender` |

### 2.4 Document Application Workflow

| Table | Description |
|---|---|
| `edoc_document` | **Core table**: one document application. Points to the document item, applicant, place (village/office), status. |
| `edoc_document_status` | Status history (workflow log): `SUBMITTED → APPROVE/SIGN → PENDING_PAYMENT → ISSUED/HANDOVER → DOWNLOADED` |
| `edoc_document_signer` | Approver/signatory (per document category or per level, signers 1..5) |
| `edoc_doc_field` | Configurable fields per document (different document types have different input fields) |
| `edoc_form_data` | Field values entered by the citizen (`doc_id`, `field_id`, `value`) |

### 2.5 Fees & Payments

| Table | Description |
|---|---|
| `edoc_invoice` | Invoice (one per document), amount derived from `edoc_doc_item.price` |
| `edoc_payment` | Payment record (method = QR scan / cash), includes QR token, payment status |
| `edoc_receipt` | Official receipt number issued to the citizen |
| `edoc_payment_acct_mapping` | Booking mapping from payment amount to accounting accounts (`debit_account`, `credit_account` → `acc_code`), linked to the budget module |

### 2.6 File Download & Archive

| Table | Description |
|---|---|
| `edoc_file_store` | Generated official document files (signed PDF), `doc_id`, `file_path`, `signed_by`, `version` |
| `edoc_download_log` | Download tracking (when the citizen downloaded) |

### 2.7 Reports / Statistics Support

| Table | Description |
|---|---|
| `edoc_stats_*` (derived) | Revenue summary, document service report, document statistics — generated by real-time JOINs of the above tables; no standalone tables usually needed. |

## 3. Key Relationships

```
[Admin hierarchy]
edoc_province ─┬─< edoc_district ─┬─< edoc_tasseng ─┬─< edoc_village ──off_id──> ap_office
               │                  │                  └─< edoc_citizen (village_id)
               │                  └────────────────────< edoc_document (village/office)

[Master data]
edoc_doc_type ─┬─< edoc_doc_item ──< edoc_document (doc_item_id)
               │           └──< edoc_service_fee
               └─< edoc_doc_field ──< edoc_form_data

[Billing]
edoc_document (citizen) ──< edoc_invoice ──< edoc_payment ──> edoc_receipt
      │                        │                       │
      └── edoc_document_status (workflow)             └─ edoc_payment_acct_mapping ──> acc_code (revenue account)
```

---

## 4. Connecting to the Budget Module

- When a document is requested, `edoc_invoice` is generated with the amount from
  `edoc_doc_item.price`.
- After payment, `edoc_payment_acct_mapping` records `debit_account_code` (cash/bank) and
  `credit_account_code` (revenue, taken from the budget module's `acc_code`).
- Thus **e-Doc collections automatically feed into the budget/finance module**, which in turn
  produces the financial reports. Both modules share the `edoc_tasaeng` database and are linked
  through accounts (no double booking).

---

## 5. Workflow / Status Flow

```
SUBMITTED → (ROUTING) PENDING_APPROVAL (notary) → ISSUED (awaiting payment)
   → PENDING_PAYMENT (citizen pays via QR) → PAID → SIGNED (issued/signed)
   → HANDOVER (ready for collection/download) → DOWNLOADED (complete)
        ↕ any stage may be REJECTED / CANCELED (reason recorded)
```

---

## 6. Users / Permissions

- The budget module already manages staff users and menus with `ap_users` / `ap_user_menus` /
  `ap_menus`.
- **Recommendation**: the e-Doc **staff (admin) side** reuses / registers via `ap_users`, or a
  separate `edoc_user`; the **citizen side** uses `edoc_citizen` (phone/email registration).
  - Exact choice to be decided at implementation time; this doc keeps both viable (distinguished
    by prefix).
